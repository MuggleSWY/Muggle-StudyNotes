# Python 程序的运行与基本错误

## 1. CPython 如何运行源代码

### 1.1 源代码、编译与字节码

Python 源代码是按照 Python 规则写出的程序内容，通常可以保存在以 `.py` 为扩展名的纯文本文件中。把一个这样的文件作为程序交给解释器执行，通常称为运行一个脚本。

**Python 是语言，CPython 是这门语言的一种具体实现。** 下面的内部运行流程以 CPython 直接运行普通、完整的 `.py` 源文件为例，不能把某一种实现的内部设计当成所有 Python 实现必须采用的方式。

理解这个流程，需要区分几个概念：

| 概念 | 含义 |
| --- | --- |
| 源代码 | 程序员按照语言规则编写的程序内容 |
| 编译 | 将代码转换成另一种表示形式，供后续处理或执行 |
| 字节码 | CPython 编译 Python 源代码后得到的内部指令形式，供其执行机制使用 |
| 机器码 | 计算机处理器能够直接执行的指令形式 |

**编译不一定直接生成机器码。** 对这里讨论的 CPython 基本流程来说，源代码会先被编译为字节码，再由 CPython 执行。

CPython 的字节码属于实现细节，可能随版本变化，其他 Python 实现也不一定采用相同的字节码。

### 1.2 一份完整源文件的基本处理过程

可以把普通源文件的处理过程分成下面几个阶段来理解：

| 阶段 | 主要工作 |
| --- | --- |
| 读取和分析源代码 | 读取文件内容，分析代码的结构，检查是否符合相应的语法规则 |
| 编译 | 将通过分析的代码转换为后续执行需要的字节码等内部形式 |
| 执行 | 按照程序的含义完成导入、函数调用、输出等操作 |

这里的阶段划分用于说明基本原理，不代表必须由用户分别执行几条命令。

**正常使用 CPython 运行源文件时，相关的分析、编译和执行通常由解释器自动完成。** 没有手动执行编译命令，不代表内部没有编译过程。

“解释器”也不意味着一定是“读取一行源代码，立即执行这一行，再读取下一行”。对于直接运行的完整源文件，CPython 会先处理这份文件的代码，再开始执行它。

### 1.3 编译完成不等于程序已经完成工作

例如：

```python
import math
print(math.sqrt(16))
```

`math` 是标准库中的数学模块，`sqrt` 是它提供的平方根函数。

这份代码被编译后，不能据此判断它已经完成了导入或输出。真正执行时，才会发生相应的操作：

1. 执行 `import math`，使当前代码可以通过名称 `math` 使用这个模块。
2. 调用 `math.sqrt(16)`，得到返回值 `4.0`。
3. 把这个值交给 `print`，由 `print` 输出。

**语法分析和编译成功，也不能保证后续执行一定成功。** 例如，`import requests` 的写法可以符合语法，但如果运行环境中找不到这个第三方模块，执行导入时仍然会出错。

判断程序时，需要区分“代码是否通过了分析和编译”与“代码执行时是否具备完成任务的条件”。

## 2. 语法错误与运行时错误

语法错误关注代码是否符合语言的书写和组合规则；运行时错误发生在程序已经开始执行、进行某项具体操作的时候。

下面用 `SyntaxError` 和 `NameError` 说明这个区别。Python 的错误不止这两种。

### 2.1 语法错误：这份源文件尚未开始执行

下面是一份完整、独立的 `.py` 文件：

```python
print("开始")
print("结束"
```

第二行缺少右括号 `)`，不符合这里的函数调用语法。CPython 在分析和编译这份文件时就会发现问题，并报告 `SyntaxError`，即语法错误。

**这份完整源文件没有通过执行前的处理，因此第一行也不会执行，不会输出“开始”。**

不能认为“第一行是正确的，所以应该先执行第一行，再在第二行停止”。在这个例子中，解释器处理的是这份完整源文件。

这个结论有明确的范围：它针对的是直接交给 CPython 运行的这份源文件。不能推广成“只要出现任何语法错误，就一定没有任何先前代码执行过”；交互式运行每次提交的代码范围不同。

### 2.2 运行时名称错误：代码开始执行后，找不到要使用的名称

假设下面也是一份完整、独立的 `.py` 文件，`math` 可以正常导入，程序没有通过其他方式提供名称 `sqrt`：

```python
print("准备计算")
import math
print(sqrt(25))
print("计算完成")
```

第三行的调用形式符合语法。问题发生在执行过程中：程序需要找到名称 `sqrt` 所指的内容，但当前代码没有可直接使用的这个名称。

关键原因是：

- `import math` 引入的是名称 `math`。
- 通过这个模块使用平方根函数时，应写成 `math.sqrt(25)`。
- 仅仅导入 `math`，不会同时把名称 `sqrt` 直接引入当前代码。

这份程序的正常输出为：

```text
准备计算
```

随后，执行第三行时会产生 `NameError`。错误信息的核心内容类似：

```text
NameError: name 'sqrt' is not defined
```

这里可以分别判断：

1. 第一行已经执行，输出了“准备计算”。
2. 第三行在取得 `sqrt(25)` 的结果时失败，因此外层的 `print` 没有输出这个计算结果。
3. 这个程序没有处理该错误的代码，执行会在此中断，第四行不会执行。
4. 前面已经完成的输出不会因为后面的错误被自动撤销。

**`NameError` 表示执行时找不到某个要使用的名称，并不专门表示“没有这个函数”。**

将第三行改为通过模块访问函数：

```python
print("准备计算")
import math
print(math.sqrt(25))
print("计算完成")
```

正常输出为：

```text
准备计算
5.0
计算完成
```

另一种可行写法是通过 `from math import sqrt` 引入名称 `sqrt`，然后使用 `sqrt(25)`。调用时采用哪种写法，要与实际引入的名称对应。

### 2.3 名称是否合法，与名称是否已经存在，是两个问题

考虑下面这份独立程序，并假设当前没有提供名称 `pritn`：

```python
print("开始")
pritn("结束")
```

`pritn` 与 `print` 的拼写不同，但 `pritn` 本身可以是一个合法名称。`pritn("结束")` 也符合这里的函数调用语法。

**`print` 是 Python 提供的内置函数的名称，不是规定函数调用必须使用这个单词的关键字。** 开发者可以为自己编写的函数选择其他合法名称。

在当前例子中，程序会先执行第一行，输出：

```text
开始
```

执行第二行时，因为找不到名称 `pritn`，会产生类似下面的错误：

```text
NameError: name 'pritn' is not defined
```

如果程序确实提供了一个名为 `pritn`、可以接受这里所传字符串的函数，这种调用写法本身就可以成立，不需要为了符合语法而改名为 `print`。

但**函数能够被调用，不代表它一定会打印传入的字符串**。调用后具体进行什么操作，由这个函数提供的功能决定；它可以输出内容，也可以把内容写入文件或完成其他工作。

| 写法 | 语法层面的判断 | 在相应条件下的执行结果 |
| --- | --- | --- |
| `print("结束")` | 调用形式合法 | 正常使用默认的 `print` 时，输出“结束” |
| `pritn("结束")` | 调用形式合法 | 如果找不到名称 `pritn`，执行时产生 `NameError` |
| `print("结束"` | 缺少右括号，调用形式不完整 | 对该源文件进行语法分析时产生 `SyntaxError` |

因此，不能把“某个名称与预期拼写不一致”直接等同于语法错误。对于这些例子，Python 会在执行相应代码时查找名称；名称可以合法，但运行时尚未提供。

### 2.4 已经完成的工作与后续代码

对于这里的运行时错误示例：

- 错误发生前已经执行的输出，不会被自动撤销。
- 没有处理该错误的代码时，当前脚本不会继续正常执行后面的语句。
- “前面执行过”和“后面会继续执行”是不同的判断。

上面的代码结果把正常输出与错误信息分开列出。“先输出、后出错”描述的是程序执行的先后关系；实际工具对正常输出和错误信息的合并显示顺序可能有所不同。

## 3. 文件运行与基本交互式运行

### 3.1 两种常见方式

| 方式 | 基本形式 |
| --- | --- |
| 文件运行 | 把源代码保存到 `.py` 文件中，将这个完整文件交给 CPython 运行 |
| 基本交互式运行 | 保持解释器运行，依次提交完整的代码输入，查看每次执行的结果 |

这是两种常见方式，不是 Python 所有运行方式的完整清单。

基本交互式界面中的一次对话可以是：

```pycon
>>> print("第一步")
第一步
>>> print("第二步")
第二步
```

`>>>` 是解释器显示的输入提示符，表示它在等待下一次输入。**提示符不属于 Python 源代码，不需要跟着输入，也不应复制到普通 `.py` 文件中。**

上面的两条代码依次在同一个交互式会话中提交；每次提交新代码，不等于重新启动一个解释器。

### 3.2 交互式运行也需要分析和编译

交互式模式不会省略必要的语法分析与编译。区别在于本次处理的代码范围：

| 方式 | 本次处理的单位 |
| --- | --- |
| 直接运行完整源文件 | 这份源文件中的代码 |
| 基本交互式运行 | 这次提交的一段完整代码输入 |

**“一次完整输入”不一定等于“一个物理行”。** 本篇示例中的单行代码已经完整，因此可以逐条提交；有些代码需要多行才能构成完整输入。

不能把交互式模式理解成“不编译”，也不能把它固定理解成“每一物理行都能独立执行”。

### 3.3 后一次输入的语法错误，不会撤销前一次执行

如果把下面两行保存在同一个 `.py` 文件中：

```python
print("开始")
print("结束"))
```

第二行多了一个右括号，存在语法错误。对这份完整文件进行处理时就会发现问题，因此第一行不会执行，不会输出“开始”。

如果是在基本交互式会话中，先提交第一条代码，等它执行完成后再提交第二条，情况就不同。下面省略具体的错误定位等细节：

```pycon
>>> print("开始")
开始
>>> print("结束"))
SyntaxError: unmatched ')'
```

第一条输入已经通过分析和编译，并完成执行。第二条输入随后才被提交，其中的语法错误不能撤销先前已经发生的输出。

对于这里这样的输入错误，基本交互式解释器报告错误后，通常还可以继续接受下一次输入。

**前一段代码不只是“语法正确”，而是已经执行完成。** 这是它的输出能够保留下来的原因。

## 4. 返回值、主动输出与交互式自动显示

### 4.1 返回值与表达式

**返回值**是函数完成调用后，交回给调用处的结果。例如，`math.sqrt(16)` 计算平方根，并返回 `4.0`。

这个结果可以继续交给其他代码使用。函数返回结果，并不等于已经把结果显示在屏幕上。

**表达式**可以先理解为能够求得一个值的代码片段。`math.sqrt(16)` 就是一个表达式，其值为 `4.0`。

### 4.2 文件运行不会自动显示这个返回值

下面是一份完整的 `.py` 文件，假设 `math` 能正常导入：

```python
import math
math.sqrt(16)
```

第二行会执行计算，并得到返回值 `4.0`。但这份文件不会自动把这个返回值显示在屏幕上，也没有把它交给后续代码继续使用。

这里需要分别判断：

| 问题 | 结果 |
| --- | --- |
| `math.sqrt(16)` 是否执行 | 执行 |
| 是否得到返回值 | 得到 `4.0` |
| 是否将这个返回值输出到屏幕 | 没有 |

**没有看到输出，不能据此判断代码没有执行。**

这个结论针对返回值的自动显示，不能扩大为“文件里的函数调用都不会输出”。如果调用的函数本身就负责输出，例如 `print`，它仍然可以在文件运行时产生输出。

### 4.3 基本交互式模式会自动显示表达式的非 None 结果

在同一个基本交互式会话中依次输入：

```pycon
>>> import math
>>> math.sqrt(16)
4.0
```

这里没有调用 `print`，仍然能看到 `4.0`，因为基本交互式模式提供了默认的结果显示机制：

**把这样的表达式单独提交后，解释器会自动显示它求得的结果；结果是特殊值 `None` 时除外。**

各自的职责是：

- `math.sqrt(16)` 负责计算，并返回 `4.0`。
- 交互式解释器负责自动显示这次表达式求得的结果。

`math.sqrt` 的功能没有因为运行方式改变而发生变化。

这个自动显示规则针对提交的表达式结果，不能理解为“程序内部每一次计算、每一个函数调用的中间结果都会被自动显示”。

### 4.4 print 自己输出内容，并返回 None

下面的代码明确调用 `print` 输出结果：

```python
import math
print(math.sqrt(16))
```

作为文件运行，或者在同一个基本交互式会话中依次提交这两条代码，都会显示一次：

```text
4.0
```

这里的过程是：

1. `math.sqrt(16)` 返回 `4.0`。
2. 这个值作为输入交给 `print`。
3. `print` 将收到的内容输出。
4. `print` 执行完成后，返回特殊值 `None`。

**`None` 本身是 Python 中的一个特殊值。** 在这里，`print` 输出内容后没有再提供一个具体的计算结果，而是返回 `None`；不能因此说它“完全没有任何返回值”，更不能说它没有执行。

基本交互式模式不会自动显示这个 `None` 返回值，因此不会在 `4.0` 后面再额外显示一行 `None`。

同时，内部 `math.sqrt(16)` 返回的 `4.0` 是交给 `print` 使用的，并不会因处于交互式环境而被提前自动显示一次。这说明“主动输出”与“自动显示最终表达式的结果”是不同的机制。

### 4.5 同一段代码在两种方式下的显示差异

假设 `math` 能正常导入：

```python
import math
math.sqrt(25)
print("计算完成")
```

作为完整的 `.py` 文件运行，显示：

```text
计算完成
```

在一个新的基本交互式会话中，按顺序逐条提交这三条代码，显示的结果依次为：

```text
5.0
计算完成
```

上面只列结果，不包含提示符和输入的代码。

两种方式下，`math.sqrt(25)` 都执行了，并返回 `5.0`。文件运行不会自动显示这个返回值；交互式模式会自动显示单独提交的这个表达式的结果。

最后一行中的 `print` 在两种方式下都负责输出“计算完成”。是否看见平方根的结果，不能用来否定已经发生的计算。
