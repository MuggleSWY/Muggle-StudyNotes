> 本地目标相对路径：`08-Agent/Agent 学习计划.md`

> 学习目标与协作方式已经明确；模块划分仍可修订，但由教学方负责专业判断，不以零基础学习者审核目录为前提。本文不是完整的课程正文。

学习者具有约两年 Java 后端开发经验，但对大模型与 Agent 几乎没有系统认识。不能因为已有后端经验，就默认已经理解模型、提示词、上下文或 Agent 的基本概念。

本计划的核心目标是：

> 成为能够独立完成真实业务任务的合格 Agent 应用开发者，并具备对现有大模型进行基础调优、评估和问题诊断的能力。

“合格”在本计划中通过实际能力检验，不以阅读完笔记、跑通框架示例或掌握大量术语代替。

| 能力方向 | 预期表现 |
| --- | --- |
| 理解与判断 | 能解释必要原理，判断需求是否需要大模型或 Agent，说明方案的能力边界与取舍。 |
| 模型使用与基础调优 | 能选择并调用适合任务的模型，组织任务指令、示例和上下文，处理输出要求，并通过实验验证改进。 |
| Agent 应用开发 | 能将工具、业务接口、知识检索、状态与执行流程组合成可工作的应用，而不是仅复制演示代码。 |
| 评估与问题诊断 | 能建立测试样例与评价标准，检查执行过程，定位问题所在环节，进行对照测试与回归验证。 |
| 工程交付 | 能完成业务集成、权限与安全约束、异常处理、部署、日志与运行观察，并管理成本和响应时间。 |

必要的架构分析和持续学习能力服务于这些目标，不把成为模型训练研究员或掌握所有前沿技术作为结业前提。

# 二、教学与规划职责

## 1. 教学方负责专业设计

教学方负责确定知识范围、模块划分、前置依赖、学习顺序、掌握深度、实践安排和验收标准，并说明重要安排的理由。要主动检查遗漏、术语堆砌、不必要的前置门槛，以及只讲框架而不讲原理等问题。

不再要求学习者判断“这几个模块是否足够”“目录是否专业合理”“是否遗漏重要知识”等尚无知识基础作答的问题。逐步规划的含义是分批解释和完善设计，而不是把课程设计责任交给初学者。

专业安排并不意味着不可质疑。资料有分歧、技术有变化或判断存在不确定性时，应说明依据和限制，并根据学习效果修订。

## 2. 学习者提供需求与学习反馈

学习者表达目标、实际开发需求以及设备、费用、时间等现实约束；在学习和实践中提出疑问，反馈不理解的概念、例子不足、节奏不合适和实践困难。

学习者不需要先具备判断课程完整性的能力，也不需要用“确认目录”承担课程质量责任。随着知识增长，学习者提出的质疑和新需求将作为改进计划的重要依据。

## 3. 当前会话与其他会话分工

当前会话用于逐步规划总体方向、模块边界、掌握深度和衔接关系，不一次性展开全部细节。

具体模块的详细内容、笔记拆分、讲解与练习，在 Agent 项目的其他会话中推进。相关会话以本总纲为共同依据，实际调整应同步记录，避免口头约定与总纲不一致。

# 三、“大模型基础调教”的课程定位

本计划将这一目标具体化为“模型应用层调优”，不能缩减成背诵提示词模板，也不能未经区分就等同于模型训练。

## 1. 作为核心实践的内容

安排任务定义、模型选择与调用、提示词与示例设计、上下文组织、模型实际支持的调用参数、输出约束与程序校验、外部知识利用、评估与失败分析等方面的学习。

要形成这样的工作方式：先明确预期结果并建立基线，再根据错误提出改进假设，进行修改和对照测试，最后检查是否引入新的问题。官方模型优化资料也将评估、提示与上下文调整、再次测量组成迭代过程。[^1]

提示词、外部知识检索和微调并不是必然依次升级的固定路线；它们解决的问题存在差异，需要根据失败原因选择方法。[^2]

## 2. 需要理解但不设为训练实践要求的内容

学习预训练、微调与应用层调优的基本区别，以及微调的适用场景、数据质量要求和评估意识。

微调涉及在已有模型基础上继续训练，与只修改提示词或补充上下文不是同一件事。[^2] 根据学习者已经明确的边界，本计划不以亲自训练或微调模型为必修实践，也不把大规模训练工程、训练算法推导和训练集群建设作为主线。

这一边界不是省略必要模型原理。凡是影响模型使用、问题诊断和设计判断的基础知识，仍需按适当深度讲清楚。

# 四、总体学习方向与模块工作稿

## 1. 三个相互衔接的方向

总体方向按“大模型基础与应用调优 → Agent 能力构建 → 可验证的工程交付”组织。

这是组织重点，不是三段互不相干的流水线。评估、安全和小型实践从早期开始，在后续不断加深。先掌握较简单方案，再学习更复杂的编排与协作；不把 Agent 数量或工具数量作为能力水平的衡量标准。Anthropic 的工程资料也强调先采用满足需求的简单方案，再依据实际收益增加复杂度。[^3]

## 2. 现有模块分类

下表保留并调整上一版的知识分类，供教学方继续检查边界与依赖。它不是行业统一标准，不是最终学习顺序，也不需要学习者先判断是否合理才能继续规划。

| 编号 | 模块工作名称 | 主要覆盖方向 | 教学定位 |
| --- | --- | --- | --- |
| 01 | 大模型与 Agent 基础 | 必要模型概念、能力与局限；大模型应用、工作流与 Agent 的关系。 | 基础必修 |
| 02 | 模型使用、提示词与基础调优 | 模型调用与选择、指令与示例、调用参数、输出要求，以及基于评估的改进。 | 核心必修 |
| 03 | 工具调用与能力扩展 | 连接业务接口及外部能力；在适当位置区分工具、MCP、Skills 与框架。 | 核心必修 |
| 04 | 上下文、知识检索与记忆 | 信息组织、外部知识利用、检索增强生成，以及任务和历史信息的管理。 | 核心必修，后续检查是否拆分 |
| 05 | 单 Agent 机制与工作流编排 | 决策与执行循环、状态、停止条件、失败恢复、人工介入和流程选择。 | 核心必修 |
| 06 | 多 Agent 协作 | 分工、交接、协调和结果整合，以及复杂度与实际收益的评估。 | 进阶内容，不是所有项目的必选方案 |
| 07 | 评估、调试与持续改进 | 评价标准、测试样例、执行记录、失败分析、对照实验与回归验证。 | 核心必修，贯穿实践 |
| 08 | 安全与权限治理 | 不可信输入、数据边界、工具权限、操作审批与风险控制。 | 核心必修，贯穿实践 |
| 09 | 工程架构、部署与运维 | 业务集成、框架应用、异常处理、部署、运行观察、性能、成本和版本管理。 | 工程重点 |

一个模块不等于一篇笔记，也不代表每个实际应用必须用到该模块中的所有能力。框架是实现手段，不能用某个框架的功能目录代替通用知识体系。

# 五、实践与能力验证

小型练习随知识推进，用于理解单项能力；综合实践连接多个模块，用于检验是否能够完成真实任务。

每个重要阶段要同时检查：能否解释原理、能否独立实现、能否验证结果、能否定位常见失败、能否说明方案边界。只看过讲解或在 AI 帮助下运行成功，不直接记为独立掌握。

综合验收应包含功能正确性、异常与边界情况、权限约束、失败诊断、运行成本和可维护性。具体评价指标与通过标准，由教学方结合实践任务设计；不预先给所有任务套用同一个成功率数字。

Java 经验作为实践优势，但不因此限定所有实验只能用 Java。主要实践语言、辅助语言、框架和环境基线，由教学方根据教学目标提出安排；仅在影响可执行性的现实条件不明确时询问学习者。

不要求先完整学完数学、机器学习、深度学习或所有编程基础，才开始做 Agent 实践；必要前置按依赖补齐。

# 六、Obsidian 笔记与跨电脑同步约定

## 1. 文件名称与标题层级

总纲文件名固定为 `Agent 学习计划.md`，本地目标相对路径为 `08-Agent/Agent 学习计划.md`。沿用学习者现有目录，不另建一套平行知识库。

以学习者 2026-09-27 本次明确说明的实际习惯为准：正文直接使用一级标题 `#` 划分主要内容，不另外添加一个用于重复笔记名称的正文主标题。此前“先写 `# Agent 是什么？`，再用二级标题划分主要内容”的约定作废。

本总纲直接从 `# 一、学习起点与核心目标` 开始，主要部分使用 `# 一、……`、`# 二、……`，其下按需要使用 `##`、`###`。保留简单、直观的序号，避免叠加 `1.1 / 1.1.1` 式编号。具体笔记继续遵循现有风格，不擅自批量修改已有笔记或另定未核实的排版规则。

例如，知识笔记可以使用文件名 `01-Agent 是什么？.md`，正文结构为：

```markdown
# 一、为什么需要 Agent

## 1. 一个具体问题

## 2. 从问题中提炼概念

# 二、核心概念与必要原理

# 三、示例与实践
```

文件名中的排序编号仅用于文件组织，不强制重复到正文中。本示例只说明标题层级，不是已经确定的第一篇教学内容。

## 2. 笔记内容与关联

正式笔记应能独立阅读，按内容需要包含概念、必要原理、例子、边界、易错点、实践与自检，而不是机械保存聊天记录。通用原理、框架实现与具体模型或版本行为应区分记录。

跨模块引用不能代替当前必要前置的解释。尚未学习但影响当前理解的知识应先补充；不影响理解的扩展内容可留待后续。

修改已有笔记时，先读取可访问的实际文件，保留学习者已经补充的内容。没有读取实际笔记时，不宣称已经核对本地格式、合并用户修改或完成本地更新。

## 3. 两台电脑通过 Git/GitHub 衔接学习

学习者已经明确的实际工作方式是：在当前电脑的 Obsidian 仓库中记录笔记，随后使用 Git 提交并推送到 GitHub；换到另一台电脑后拉取更新，再继续学习和记录。换机时重复这一过程，不改用其他同步方案作为默认要求。

建议的日常衔接顺序为：

```text
开始学习：检查当前电脑的工作区状态 → 妥善处理未提交改动 → 拉取远端更新
本次学习：阅读、实践、修改笔记 → 更新实际学习进度
结束学习：检查差异 → 提交需要同步的文件 → 推送到 GitHub
切换电脑：在另一台电脑检查工作区并拉取更新 → 继续学习
```

其中，`push` 用于将本地提交对应的更新发送到远端，`pull` 用于获取并整合远端更新；不能把仅在本机保存文件视为已经完成跨电脑同步。[^5][^6] 具体命令、远端名称与分支名称以实际仓库为准，本总纲不擅自更改现有 Git 配置。

为配合这一工作方式，后续笔记与示例遵守以下约束：

- 笔记与必要附件采用仓库内可迁移的组织方式，引用优先使用库内链接或相对路径，不把某一台电脑的盘符、用户名路径或对话下载链接作为唯一依赖。
- 保留现有附件目录与命名习惯；不擅自改动 `.obsidian`、`.gitignore`、分支或远端配置。需要调整时先说明原因。
- 发生冲突时先保留并核对双方内容，不为了同步而直接覆盖、强制推送或丢弃已有笔记。
- 实践中使用的 API Key、访问令牌和密码不写入待同步的笔记或示例配置；示例仅使用占位符。

这些是同步约定和建议，不表示已经检查、修改或操作了学习者的 GitHub 仓库。

## 4. 区分下载文件、本地保存与远端同步

Obsidian 的笔记是本地仓库目录中的 Markdown 文件。将 `.md` 文件实际放入当前打开的仓库，才完成了该文件的本地落盘；仅在对话中生成或展示文件，并不等同于保存到了本地仓库。[^4]

交付和更新时必须区分以下状态：

| 状态 | 可以报告的事实 |
| --- | --- |
| 已生成对话下载文件 | 已在对话工作区创建可下载的 Markdown 文件；不代表本地目录已有该文件。 |
| 已保存到本地仓库 | 只有实际写入并核实本地目标路径，或学习者明确反馈已保存后，才能报告本地保存完成；应说明确认来源。 |
| 已提交到本地 Git | 只有实际提交并核实成功，或学习者明确反馈提交完成后，才能报告这一状态。 |
| 已推送到 GitHub | 只有实际推送并核实成功，或学习者明确反馈推送完成后，才能报告远端同步完成。 |

本次 v0.3 的交付状态仅为“已生成对话下载文件”；本地目标仍为 `08-Agent/Agent 学习计划.md`。后续以仓库中的同名文件持续修订，版本变化记录在正文，不要求每次另建一个带版本号的笔记。
