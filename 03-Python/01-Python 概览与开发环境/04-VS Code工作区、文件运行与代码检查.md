# VS Code 工作区、文件运行与代码检查

## 一、开发工具与 Python 运行环境的关系

### 1. VS Code 不等于 Python 解释器

VS Code 是开发工具，负责编辑代码、管理文件，并提供运行、调试等操作入口。Python 解释器负责执行 Python 程序。Python 扩展将解释器选择、文件运行等功能接入 VS Code；安装扩展不等于安装解释器。

例如，开发工具可以把 `hello.py` 交给 `C:\Development\Python\Python314\python.exe` 执行，也可以把同一文件交给项目 `.venv` 中的解释器执行。代码文件和解释器是两种不同的文件，二者不需要放在同一目录或同一磁盘中。

**编辑器决定怎样组织开发操作，解释器及其环境决定程序在哪里执行、能够使用哪些已准备好的软件包。**

### 2. VS Code 与 PyCharm 的选择

VS Code 偏向通用编辑器，通过扩展组合不同语言的开发能力。PyCharm 是以 Python 开发为中心的集成开发环境，将许多相关能力集中提供。两者都能编辑、运行和调试 Python 程序，也能使用已有的虚拟环境。

系统学习 Python 并不要求必须选择其中一个。VS Code 适合在同一工具中处理 Python、前端代码和文档；熟悉 IntelliJ IDEA 的开发者，也可能更容易适应 PyCharm 的界面组织。实际选择应结合使用习惯和工作需求，而不是认为某一种工具只能写小脚本、另一种才能开发正式项目。

项目中的 `.py` 文件不属于某个编辑器的专用格式，`.venv` 也不属于 VS Code。换用 PyCharm 时可以打开原项目、选择原有解释器；但两个开发工具各自的设置不会自动互相转换。

## 二、目录、工作区与工作区信任

### 1. 分开存放解释器和项目代码

以下是一组具体目录示例：

| 用途 | 路径 |
|---|---|
| 基础 Python 安装目录 | `C:\Development\Python\Python314` |
| Python 学习目录 | `D:\Study\Python` |
| 当前练习项目 | `D:\Study\Python\01-environment` |
| 项目中的虚拟环境 | `D:\Study\Python\01-environment\.venv` |

`Python314`、`Python`、`01-environment` 都是用于整理文件的名称，不是 Python 强制要求。`Python314` 这个文件夹名不能单独证明解释器的实际版本，版本应通过运行检查确认。

自己的代码应保存在项目目录中，不要混入解释器安装目录，也不要放进 `.venv` 的内部目录。

### 2. 打开文件夹形成工作区

在 VS Code 中选择“文件 → 打开文件夹”，打开：

```text
D:\Study\Python\01-environment
```

左侧资源管理器出现 `01-environment` 根目录后，这个文件夹就构成当前的单文件夹工作区。工作区用于确定当前管理的文件范围，并承载工作区级别的开发设置。

打开一个普通文件夹即可开始使用这种工作区，不需要先创建特殊的“Python 项目工程文件”。

### 3. `.vscode/settings.json` 的用途

单文件夹工作区中，`.vscode/settings.json` 可以保存这个工作区的 VS Code 设置。它是编辑器配置文件，不是 Python 源代码文件。练习程序应另建为 `hello.py` 等文件，不应直接写进 `settings.json`。

设置可能来自用户级配置、工作区配置或工具自己的配置文件。因此，同一个扩展在不同项目中的行为不一定相同；没有查看实际配置之前，不应随意覆盖设置。

### 4. 信任范围应与代码来源相匹配

工作区处于“受限模式”时，VS Code 会限制终端、调试、任务和部分扩展能力，以降低陌生项目自动执行代码的风险。

对于自己创建、来源明确的练习目录，可以通过顶部提示栏的“管理”或工作区信任页面，信任当前文件夹。不要为了省去提示，顺带信任来源不明的项目或不必要的上级目录。

“已信任”表示允许启用相应开发功能，不表示 VS Code 已证明目录中的所有代码安全，也不表示 Python 解释器已经配置正确。

## 三、Python 扩展的职责与使用边界

### 1. 常见 Python 扩展的分工

| 扩展 | 主要作用 |
|---|---|
| Python | 提供 Python 开发入口，连接解释器选择、运行和测试等操作 |
| Pylance | 提供代码补全、参数提示、导航和代码分析 |
| Python Debugger | 提供断点、逐步执行和变量查看等调试支持 |
| Python Environments | 提供环境发现、选择、创建及软件包管理的界面 |
| Ruff | 检查部分代码问题与风格规则，并提供格式化、导入整理和部分修复能力 |

这些扩展不是五种 Python 解释器，也不是运行 Python 必须全部具备的组件。它们主要改善开发体验，真正执行程序的仍然是选定的解释器。

安装了某个扩展，不等于它的全部功能都已启用或已配置好。例如，装了 Ruff，并不能据此判断保存时自动修复已经开启。

### 2. 按用途管理扩展

Java、Vue、Markdown 等扩展服务于不同任务。某个扩展在当前 Python 项目中暂时用不到，不代表它没有价值；也不能仅凭扩展总数判断性能问题。

需要减少当前项目中的干扰时，可以使用扩展齿轮菜单中的“禁用（工作区）”。这与全局禁用、卸载不同：工作区禁用保留安装，并限制当前工作区中的启用状态。

格式化器也要按语言分工。Ruff 面向 Python；Prettier 的常规内置语言支持不包括 Python。一个项目可以同时安装不同语言所需的工具，但同一类文件应明确采用哪个格式化器，避免配置不清导致反复修改。

### 3. 检查、格式化与运行不能混为一谈

**代码检查**在不按正常业务流程运行整个程序的情况下分析代码，提示潜在问题或不符合规则的写法。**格式化**调整空格、换行等排版。**运行**则让解释器实际执行程序。

程序能运行，不代表符合项目规范；检查工具没有报错，也不代表程序逻辑一定正确。代码风格值得认真维护，但不能把风格提示误认为 Python 语法错误。

## 四、选择解释器与运行文件

### 1. 通过路径确认解释器

按 `Ctrl + Shift + P` 打开命令面板，执行：

```text
Python: Select Interpreter
```

基础解释器示例：

```text
C:\Development\Python\Python314\python.exe
```

项目虚拟环境解释器示例：

```text
D:\Study\Python\01-environment\.venv\Scripts\python.exe
```

两个解释器可以显示相同的 Python 版本，但属于不同环境。选择时应核对路径，不能只核对版本号。

如果环境未被自动发现，可以使用“输入解释器路径”或“浏览”指定已经存在的解释器。不要仅因列表暂未显示，就重复创建环境。

状态栏显示的环境是开发工具选择的信息；实际运行时，还应结合终端命令核对调用路径。列表中“全局”标签描述基础环境类别，不等于 Windows 安装器中的“为所有用户安装”。

### 2. 建立并保存源代码文件

在 `01-environment` 根目录中新建 `hello.py`，内容如下：

```python
import math

print("开始运行 Python 文件")
print(math.sqrt(81))
print("文件运行结束")
```

按 `Ctrl + S` 保存。代码中的空行用于分隔导入区域和普通执行语句；`math.sqrt(81)` 返回 `9.0`，外层 `print` 将其输出。

源文件中不要写入 `>>>`、`PS ...>` 等提示符，也不要把预期输出当作代码粘贴进去。提示符是交互工具显示的界面内容。

**保存与运行是两个动作。** 保存把编辑内容写入磁盘；运行把程序交给解释器。文件标签上未保存状态的提示可以帮助判断是否还有修改尚未写入文件。

### 3. 运行整个文件并核对输出

保持 `hello.py` 为当前编辑文件，打开命令面板，执行：

```text
Python: Run Python File in Terminal
```

正常情况下，终端中会先显示运行命令，随后显示：

```text
开始运行 Python 文件
9.0
文件运行结束
```

使用项目虚拟环境时，运行命令中的解释器应指向 `.venv\Scripts\python.exe`，后面跟随 `hello.py` 的路径。

这里有两个路径需要分别阅读：前者表示“谁来执行”，后者表示“执行哪个文件”。项目文件保存在 D 盘，并不会自动决定应使用哪个 Python 环境。

对于这个顺序执行的简单程序，执行到文件末尾即可结束，不需要加上用于退出交互式会话的 `exit()`。

## 五、集成终端、提示符与当前目录

VS Code 底部的“终端”和“调试控制台”不是同一个输入位置。执行 PowerShell 命令应使用终端中正在运行的 PowerShell；调试控制台服务于调试过程，不能当作 PowerShell 随意输入系统命令。

| 提示符示例 | 当前接受输入的程序 |
|---|---|
| `PS D:\Study\Python\01-environment>` | PowerShell |
| `(.venv) PS D:\Study\Python\01-environment>` | 通常表示已激活虚拟环境的 PowerShell |
| `>>>` | Python 交互解释器 |

终端标签名不一定随其内部启动的程序变化。判断输入位置，应关注实际提示符和当前程序，而不是只看标签写着“Python”还是“PowerShell”。

例如，在 `>>>` 后输入 `Get-Location` 或激活脚本路径，并不是在执行 PowerShell 命令，而是把它交给 Python 处理，可能产生语法错误或名称错误。

在 PowerShell 中：

```powershell
Get-Location
```

用于查看当前目录。下面这条命令：

```powershell
where.exe python
```

用于查找匹配的外部程序文件位置。它不等于完整的 PowerShell 命令解析检查；如果另有同名别名或函数，仍需进一步核查。当前环境中没有发现这类覆盖时，它可用于观察 PATH 中相关入口的顺序。

`python --version` 只能帮助确认实际启动程序报告的版本，不能区分所有同版本的环境。核查时应将版本、路径与当前目录结合起来。

## 六、读懂并处理 Ruff 提示

### 1. 先确认来源和规则编号

遇到黄色波浪线时，将鼠标放上去，或打开底部“问题”面板，查看完整文字、工具名称和规则编号。

| 提示 | 检查重点 |
|---|---|
| `Ruff(I001)`：导入区域未正确排序或格式化 | 导入区域的组织、排序、分组和排版 |
| `Ruff(F401)`：导入后未使用 | 导入的名称没有被后续代码使用 |

规则编号比“有黄线”更能说明问题。不能仅根据同样的黄色波浪线，就认定本次仍是上一次的原因。

### 2. I001 不等于某一种固定空格错误

下面这段代码可用于观察导入区域的排版：

```python
import math

print(math.sqrt(81))
```

在采用 Ruff 默认相关行为时，导入区域后接这种普通执行语句，保留一行空行即可。这里不是“至少空一行，空得越多越规范”。

文件最外层的函数、类定义有不同的空行约定；项目也可以配置导入后的空行数量。不能把某个位置的一行空行规则推广到所有代码位置。

I001 是导入区域的综合检查。对于只有一条导入的代码，没有多个导入之间的排序问题，但仍可能存在空行或其他排版差异。截图通常看不到空格、Tab 等字符，历史警告的具体原因不能仅凭截图完全还原。

使用 `Ctrl + .` 打开快速修复后，应明确选择 Ruff 的“Organize imports”，并观察实际修改。如果手动修正后仍出现警告，应检查有效配置，而不是反复猜测要多加几行空行。

### 3. 空格、换行与空行

按空格键是在当前行中增加字符；按 Enter 才会换行。一行看起来为空，也可能已经包含空格或 Tab。

作为代码分隔，宜使用不含额外空白字符的空行，并避免行尾多余空格。空行的数量应服务于代码结构和项目规则。

在 VS Code 设置中搜索 `editor.renderWhitespace`，将显示方式设为 `all`，可以让空格、Tab 等字符更容易识别。这个设置只改变显示方式，不会替你修改源文件。

### 4. F401 要结合程序目的处理

假设所选解释器中已经安装 `requests`：

```python
import requests

print("requests 导入成功")
```

执行到第二条语句，可以证明前面的导入没有失败。但固定字符串中出现 `requests`，并不等于代码实际使用了名为 `requests` 的模块，所以 Ruff 仍可能报告 F401。

这段程序的目的就是检查导入是否成功。直接自动删除第一行，会让它失去验证作用。因此，自动修复必须结合程序目的判断。

可以进一步读取版本信息：

```python
import requests

print("requests 导入成功")
print("requests 版本号为：", requests.__version__)
```

`requests.__version__` 是 Requests 提供的版本信息属性，通过点号访问；它是一个值，不是在调用函数，因此后面不加调用括号。不能假定所有第三方库都提供同名属性。

这里确实使用了 `requests` 名称，因而解决了“导入后未使用”的问题；导入排版是否合规仍由 I001 等规则分别判断。程序只是导入并读取信息，没有发送 HTTP 请求。

## 七、运行结果、注释和规范分别验证

字符串之外的 `#` 可以开始注释，注释延续到该行末尾。例如：

```python
print(math.sqrt(81))  # 输出 9.0
```

注释解释代码，但不参与计算。把注释误写成“输出 4.0”不会改变程序结果，却会误导阅读者，因此修改代码后也要同步维护注释。

检查一个小程序时，应分别观察：解释器路径是否正确、程序是否完成预期操作、结果是否正确、注释是否一致、工具规范检查是否通过。不能以其中一项通过替代其他判断。

如果显示“0 个错误、0 个警告”，只能说明当前已启用检查没有报告问题，不能据此声称程序经过了所有可能的检查。
