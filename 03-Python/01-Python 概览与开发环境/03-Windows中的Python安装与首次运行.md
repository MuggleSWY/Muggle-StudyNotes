# Windows 中的 Python 安装与首次运行

## 1. 获取 Python 的不同方式

### 1.1 语言、实现与发行版

准备环境时，需要区分语言、实现和发行版：

| 概念 | 含义 | 例子 |
| --- | --- | --- |
| 编程语言 | 编写程序时遵循的规则 | Python |
| 语言实现 | 实际支持这些规则、执行程序的软件实现 | CPython、PyPy |
| 发行版 | 将解释器、库和工具等内容组合起来，提供安装与使用方式 | python.org 提供的 CPython 发行版、Anaconda Distribution |

Anaconda 通常指 Anaconda Distribution。它通常包含 CPython 解释器、conda 和一批预装的软件包。**安装 Anaconda，通常已经同时安装了可以运行 Python 的解释器。**

Anaconda 与 CPython 属于不同层次：前者描述软件如何组合和提供，后者描述 Python 的一种实现。不能把 Anaconda 简单列为与 CPython、PyPy 并列的另一种解释器实现。

不同安装方式中的 Python 语言知识可以相互迁移，但具体工具、目录、版本和可用库可能不同。

### 1.2 python.org、Anaconda 与 Miniconda

| 获取方式 | 主要特点 |
| --- | --- |
| python.org 提供的常规 CPython 安装 | 提供解释器、标准库及相关工具；Windows 传统安装器通常可同时安装 pip，其他库按需要添加 |
| Anaconda Distribution | 提供 Python、conda、图形管理工具和较多预装软件包，初始环境包含的内容较多 |
| Miniconda | 安装内容较精简：包含 Python、conda 及必要依赖，其他软件包按需要添加 |

Anaconda 常用于数据分析和科学计算，也可以编写一般的 Python 程序；通过 python.org 安装的 Python，同样可以安装相应的库开展数据分析等工作。安装方式不会把 Python 的用途固定在某一领域。

**预装状态不会改变库的归属。** 某个第三方库即使随 Anaconda 一起安装，也仍然是第三方库，不会因此成为 Python 标准库。

Anaconda 发行版自身的发布编号，与其中某个环境里的 Python 版本号，需要分别查看。不同 conda 环境可以使用不同版本的 Python。新建的环境也不会自动继承初始 `base` 环境中全部预装的软件包。

### 1.3 pip、venv 与 conda 的职责

| 工具或模块 | 主要职责 |
| --- | --- |
| pip | 安装和管理 Python 软件包，例如安装、查看和卸载第三方包 |
| venv | 基于已经存在的 Python 安装，创建供项目使用的隔离环境 |
| conda | 管理环境和软件包，也可以为环境安装、管理 Python 版本 |

pip 本身不负责创建项目虚拟环境；venv 本身不负责下载并安装任意另一个 Python 版本。conda 则可以把 Python 作为环境中的一个软件包来管理。

这些工具的职责有联系，但不能仅因为都与“环境”有关，就把它们理解为同一种工具。

## 2. 理解版本号与 Windows 安装包

### 2.1 实现、版本与平台是不同维度

以 `CPython 3.14.9，Windows 64-bit` 为例：

| 部分             | 含义                                     |
| -------------- | -------------------------------------- |
| CPython        | 使用的 Python 实现                          |
| 3              | Python 的主版本                            |
| 3.14           | 所属的功能版本系列                              |
| 3.14.9         | 3.14 系列中的一个维护版本，最后的 `9` 是维护版本编号        |
| Windows 64-bit | 安装包面向的操作系统与平台类型；这里的常规 64-bit 安装包面向 x64 |

`3.14.9` 可以作为固定示例，不能因此把它理解为永远最新的版本，或适合所有项目的唯一选择。选择版本时，需要结合维护状态、项目要求和依赖支持情况。

版本系列之间可能增加或调整语言和库功能；同一系列的维护版本主要提供问题修复等更新。比较版本时，需要看完整编号。

### 2.2 下载类型要与用途和设备匹配

Windows 发布文件中可能同时出现：

| 下载项 | 主要用途 |
| --- | --- |
| Windows installer (64-bit) | 面向 x64 Windows 的常规安装器 |
| Windows installer (32-bit) | 面向相应 32 位运行需求的安装器 |
| Windows installer (ARM64) | 面向 ARM64 平台的安装器 |
| Windows embeddable package | 为把 Python 嵌入其他应用提供的精简分发形式 |
| Source release | 源代码，供自行构建等用途使用 |

选择 x64 或 ARM64，需要看设备和系统架构，不能只根据“都是 64 位”就互相替代。

普通开发环境可以使用常规安装方式。嵌入式包与完整开发环境的用途不同，不应只因为它的下载体积较小就把它当作等价安装包。

### 2.3 传统安装器与 Python install manager

Python install manager 是用于安装、管理和启动 Python 版本的工具。它与传统的版本专用 `.exe` 安装器，是不同的安装入口。

传统安装器从 Python 3.14 起进入弃用阶段，官方继续为 3.14 和 3.15 提供它，3.16 及以后不再提供这种传统安装器。新的 Windows 安装管理方式使用 Python install manager。

**安装工具的版本号与它管理的 Python 版本号不是同一个编号。** 不能根据管理器自己的版本号，判断它实际安装了哪个 Python。

以下安装界面说明，以 Python 3.14.9 的传统 Windows 安装器为例。对应版本可从 [Python 3.14.9 发布页面](https://www.python.org/downloads/release/python-3149/) 的 Files 表格中选择；页面顶部的安装管理器按钮则属于另一个入口。

## 3. 终端、PowerShell 与 Python 解释器

### 3.1 各自负责什么

| 名称 | 职责 |
| --- | --- |
| 终端软件或终端窗口 | 提供文字输入和输出的界面，例如 Windows Terminal |
| PowerShell | 处理命令和脚本，查找并启动其他程序；它有自己的语法 |
| Python 解释器 | 按照 Python 的规则执行 Python 代码 |
| 编辑器 | 帮助编写和保存代码，例如 VS Code |

在终端窗口中启动 Python 后，窗口可能仍保留原来的 PowerShell 标签。窗口标签并不能单独说明当前输入由谁处理。

例如：

```text
PS C:\Windows\system32>
```

这是 PowerShell 提示符。中间的 `C:\Windows\system32` 是当前工作目录，即这次终端会话目前所在的文件夹。

启动 Python 交互环境后，常见提示符变成：

```text
>>>
```

这表示 Python 解释器正在等待输入。**`PS ...>` 和 `>>>` 都是界面显示的提示符，不需要跟着输入。**

当前工作目录、Python 安装目录和项目目录，可以是不同的位置。

### 3.2 PATH 帮助查找命令

环境变量可以理解为操作系统和程序使用的一组命名配置信息。`PATH` 是其中之一，保存一组供查找外部命令时使用的目录。

假设 Python 安装在：

```text
C:\Development\Python\Python314
```

安装目录加入 PATH 后，PowerShell 等命令行程序可以在相应目录中查找 `python.exe`。因此，即使当前工作目录不是 Python 安装目录，也可以通过 `python` 命令启动它。

需要分别理解：

- 安装 Python：将解释器和配套文件准备到指定位置。
- 配置 PATH：帮助命令行根据名称找到程序。
- 启动 Python：实际运行已经找到的解释器程序。

没有加入 PATH，不代表解释器没有安装。程序也可以通过完整路径或工具中明确配置的解释器路径来启动。

## 4. 安装之前核查已有环境

### 4.1 查询命令文件

在 PowerShell 中可以依次执行：

```powershell
where.exe python
where.exe python3
where.exe py
```

这里保留 `.exe`，是为了明确调用 Windows 的文件查找程序。PowerShell 中的 `where` 通常还是另一个命令的别名，含义不同。

这些查询会在当前目录和 PATH 指定的目录范围内查找匹配文件。它们适合了解命令入口，但不是对整台电脑做完整的软件安装盘点。

| 查询结果 | 可以说明什么 | 不能直接推导什么 |
| --- | --- | --- |
| 找到一个路径 | 在查询范围内找到了匹配文件 | 不能仅凭路径证明它是可正常使用的 Python 解释器 |
| 找到多个路径 | 存在多个匹配入口，需要结合来源判断 | 不能把所有结果都当成独立、完整的 Python 安装 |
| 没有找到 | 查询范围内没有找到匹配文件 | 不能证明整台电脑完全没有 Python |

PowerShell 还可能通过自身的别名、函数等机制解析命令。`where.exe` 是文件查询工具，不能代替对所有命令解析机制的检查。

### 4.2 识别 Windows 的应用执行别名

查询结果可能包含类似路径：

```text
C:\Users\<用户名>\AppData\Local\Microsoft\WindowsApps\python.exe
```

其中 `<用户名>` 是说明用的占位文字，实际结果中会显示真实的 Windows 用户目录名。

Windows 可以通过“应用执行别名”提供某个命令入口。初次核查时，可以进入：

**设置 → 应用 → 高级应用设置 → 应用执行别名**

如果 `python.exe` 或 `python3.exe` 的所属应用是 **App Installer**，它可以是引导安装 Python 的入口。这个入口本身不等于已经准备好的 Python 运行环境。

**不能仅凭 WindowsApps 这个目录名断定某个入口是假解释器。** 正常安装的软件和新的安装管理工具也可能使用应用执行别名，需要结合所属应用及实际行为判断。

某些入口可能打开安装引导或触发安装管理器的行为。因此，尚未确认来源时，先查询入口和归属，有助于避免把“查环境”直接变成“安装环境”。

### 4.3 结合其他信息判断

“安装的应用”中可以搜索 Python，也应根据使用经历关注 Anaconda、Miniconda 等名称。曾经使用过某种安装方式，还需要分清它是在当前电脑还是另一台电脑上。

编辑器图标、VS Code 扩展或 PyCharm 的存在，都不能单独证明已经有可用的 Python 解释器。编辑器可能需要另外选择、创建或安装运行环境。

对于未加入 PATH 的安装、便携环境或工具管理的环境，常规命令查询和应用名称搜索可能看不到全部情况。应根据实际线索补充核查，再决定复用现有环境或新增安装。

## 5. 安装目录与安装范围

### 5.1 安装目录可以自定义

可以采用这样的目录结构：

| 目录 | 用途 |
| --- | --- |
| `C:\Development` | 统一存放开发工具 |
| `C:\Development\Python` | 集中存放 Python 安装 |
| `C:\Development\Python\Python314` | 存放某个 Python 3.14 安装及配套文件 |

`Python314` 只是便于识别的目录名称，实际版本由安装包及其中的软件决定。文件夹名称不会把解释器切换成另一个版本。

安装目录用于存放解释器、标准库和配套工具；项目目录用于存放自己编写的源代码和项目资料。两者应按用途分别组织。

### 5.2 当前用户与所有用户

安装位置决定文件存放在哪里；安装范围决定安装器为哪些 Windows 用户注册和配置相应功能。两者是不同设置。

将安装位置改为 `C:\Development\Python\Python314`，不会自动勾选“为所有用户安装”。按当前用户安装时，选定目录仍需要有适当的写入权限。

“按当前用户安装”也不应被解释为其他用户在文件权限允许时绝不可能执行其中的程序。它首先描述安装器的注册和配置范围。

## 6. 传统安装器首页

| 选项 | 作用 | 一种适合个人学习环境的选择 |
| --- | --- | --- |
| Install Now | 使用默认配置和界面显示的默认位置安装 | 需要查看组件和位置时，可改走自定义安装 |
| Customize installation | 逐步选择组件、安装位置和高级选项 | 进入此流程 |
| Use admin privileges when installing py.exe | 以管理员权限为所有用户安装 `py.exe` 启动器 | 采用当前用户方式时不勾选 |
| Add python.exe to PATH | 将解释器安装目录及相关命令目录加入 PATH | 勾选 |

这里需要区分两个程序：

| 名称 | 作用 |
| --- | --- |
| `python.exe` | 执行 Python 程序的解释器程序 |
| `py.exe` | 帮助查找、选择并启动解释器的入口 |

这里按传统安装器中的启动器说明。新版 Python install manager 也可能提供 `py` 命令；同名入口在不同安装方式下可能具有不同能力，使用说明应与实际工具对应。

传统安装器中的管理员复选框，针对的是启动器的安装权限和范围。未勾选该框，不等于不安装启动器；是否安装启动器组件，还由后续组件选项决定。

它也不表示以后运行普通 Python 程序必须使用管理员权限。

## 7. Optional Features：可选组件

| 选项 | 安装的内容 | 示例选择 |
| --- | --- | --- |
| Documentation | Python 本地文档，便于离线查阅 | 保留 |
| pip | Python 包管理工具 | 保留 |
| Tcl/Tk, turtle and IDLE | 图形支持、绘图功能和 IDLE 开发工具 | 保留 |
| Python test suite | Python 自身及标准库的测试文件 | 普通学习环境可以不安装 |
| py launcher | `py` 启动器 | 保留 |
| for all users | 为所有 Windows 用户安装旁边的 `py launcher` | 当前用户安装时不勾选 |

### 7.1 图形支持与 IDLE

这组选项包含相互关联的内容：

- Tcl/Tk 提供创建窗口、按钮等图形界面的基础支持。
- `tkinter` 是 Python 使用 Tcl/Tk 的标准接口。
- `turtle` 提供通过代码控制画笔移动的绘图功能，依赖相应的图形支持。
- IDLE 提供代码编辑和 Python 交互等功能，也依赖这组支持。

即使主要使用 VS Code 编写代码，程序仍可以调用这些图形功能。保留这一组选项，并不要求必须改用 IDLE。

### 7.2 Python test suite 与自己的测试

Python test suite 包含用于检验 Python 自身行为的测试文件。普通应用开发通常不需要这组自测文件。

**不安装 Python test suite，不等于删除标准库中的 `unittest` 等测试工具。** 以后仍然可以给自己编写的程序添加测试。

pip 随安装器一起提供，也不使它成为 Python 的语法或标准库功能。安装包中同时提供的组件，可能具有不同的来源和职责。

## 8. Advanced Options：高级选项

| 选项 | 作用 | 示例选择 |
| --- | --- | --- |
| Install Python 3.14 for all users | 为所有 Windows 用户注册和配置 Python 安装 | 不勾选 |
| Associate files with Python | 为 `.py` 等文件注册与 Python 启动器的关联 | 保留勾选 |
| Create shortcuts for installed applications | 创建安装组件的快捷方式，例如开始菜单入口 | 保留勾选 |
| Add Python to environment variables | 将实际安装目录及其 Scripts 子目录加入相应 PATH | 保留勾选 |
| Precompile standard library | 在安装时预先编译标准库的 Python 源文件 | 不勾选也可以正常使用 |
| Download debugging symbols | 下载用于底层调试的符号文件，帮助调试器对应源码位置 | 不勾选 |
| Download debug binaries | 下载用于底层开发调试的解释器调试构建 | 不勾选 |
| Download free-threaded binaries | 额外安装自由线程构建 | 使用常规构建时不勾选 |

这里“为所有用户安装 Python”的选项，控制 Python 本身的安装范围；上一页启动器旁的 `for all users` 控制启动器的范围，不能把两者混为一个设置。

文件关联用于登记某类文件可由什么程序处理；实际默认打开方式也可能受到 Windows 既有设置影响。

### 8.1 预编译只是把一部分工作提前做

CPython 执行 Python 源代码时涉及编译。预编译标准库，会把适用的标准库源文件提前编译，并生成字节码缓存，通常以 `.pyc` 为扩展名。

未勾选这一选项，只是没有在安装阶段提前完成这部分工作。解释器仍可以在需要时编译相应源代码。

不能把“不预编译标准库”理解成“Python 以后不再编译”。

### 8.2 日常调试可以使用常规解释器

调试符号和解释器调试构建，主要面向解释器、本地扩展等底层开发调试。

给自己写的普通 Python 程序设置断点、逐步执行和查看变量，可以使用常规解释器。这两项下载不是日常 Python 源码调试的必要前提。

选项文字中的 VS 指 Visual Studio。

### 8.3 free-threaded 是另一种 CPython 构建

自由线程构建用于支持同一解释器中的多个线程并行执行 Python 代码。这涉及线程与并发运行机制，与是否能编写普通 Python 程序是不同的问题。

安装这种构建，不会自动把普通代码变成并行程序，也不能保证任何程序都更快或所有依赖都已经兼容。基础环境可以先使用常规构建。

## 9. 安装完成后的长路径选项

安装器显示 `Setup was successful`，说明安装过程报告成功。完成页还可能提供：

```text
Disable path length limit
```

它用于启用 Windows 的长路径支持。

“路径长度”指完整文件路径的长度，包括盘符、各级目录和文件名。Windows 的部分传统文件操作存在约 260 个字符的路径长度限制；启用相应设置后，Python 等支持该机制的程序可以处理更长的路径。

这个选项修改的是 Windows 系统设置，需要管理员权限。项目或依赖的目录层级较深时，启用它有助于减少相关限制带来的问题。

需要保留两个边界：

- 它作用于支持长路径机制的程序，不能把它理解成所有程序、所有文件名都从此没有长度限制。
- 路径长度与 PATH 环境变量是两个概念。前者关注一个文件位置有多长，后者保存用于查找程序的目录列表。

已运行的某些进程可能需要重新启动，才会采用新的系统设置。安装成功与是否已经启用长路径支持，也应分别判断。

## 10. 验证安装位置与版本

### 10.1 使用新打开的终端

安装器修改 PATH 后，已经打开的终端可能仍使用原来的环境信息。可以关闭旧终端，再通过 Win + R 输入 `powershell`，打开新的 PowerShell 窗口。

若使用其他应用中的内置终端，也可能需要重新打开所属应用，使新会话获得更新后的环境信息。

在 PowerShell 中依次执行：

```powershell
where.exe python
python --version
py --version
```

| 命令 | 验证的内容 |
| --- | --- |
| `where.exe python` | 查询匹配程序文件的位置 |
| `python --version` | 经 `python` 命令启动解释器，显示版本号 |
| `py --version` | 经启动器启动解释器，显示所选解释器的版本号 |

`--version` 是命令行选项，表示显示版本号后退出。因此执行后会回到 PowerShell，不会停留在 Python 交互提示符中。

### 10.2 如何解读输出

采用上面的示例路径时，文件查询结果中应能找到：

```text
C:\Development\Python\Python314\python.exe
```

如果两种启动方式都选择了示例中的版本，版本输出分别为：

```text
Python 3.14.9
```

查询结果还可能同时列出此前确认过的 WindowsApps 应用执行别名。出现多行结果本身不是安装失败的证据，应结合入口来源、顺序及实际执行结果判断。

两个启动命令显示相同版本号，说明它们都能启动该版本的解释器；**仅凭相同版本号，还不能证明它们指向同一个可执行文件。**

这组命令用于基础验证，也不等于证明整台电脑只有一个环境，或所有第三方包、编辑器和项目都已经配置完成。

## 11. 启动、使用与退出交互环境

### 11.1 启动交互环境

在 PowerShell 中输入：

```powershell
python
```

这次没有附带 `--version`。在正常的交互终端中，解释器会显示启动信息，并等待输入 Python 代码。

| 提示符 | 当前交互对象 |
| --- | --- |
| `PS C:\某个目录>` | PowerShell |
| `>>>` | Python 交互解释器 |

窗口标题可以保持不变；判断当前输入应采用哪种语言，要结合正在运行的程序和提示符。

### 11.2 一个完整会话示例

下面省略解释器启动横幅，保留命令、提示符和结果：

```text
PS C:\Windows\system32> python
>>> import math
>>> print("开始计算")
开始计算
>>> print(math.sqrt(36))
6.0
>>> print("计算完成")
计算完成
>>> exit()
PS C:\Windows\system32>
```

这里依次发生了：

1. PowerShell 启动 Python。
2. Python 执行 `import math`，引入数学模块的名称。
3. `print` 输出开始提示。
4. `math.sqrt(36)` 计算并返回 `6.0`，再由外层的 `print` 输出。
5. `print` 输出完成提示。
6. `exit()` 结束当前 Python 交互会话，控制回到 PowerShell。

示例中先导入 `math` 再输出开始提示，可以正常工作；使用 `math.sqrt` 时，相应名称已经可用。

提示符和显示出的结果都不是需要再次输入的代码。交互环境适合逐条执行和观察，窗口中出现过代码，也不意味着已经把它保存成可维护的 `.py` 源文件。

### 11.3 为什么有时只输入 exit 也能退出

`exit()` 可以作为普通 Python 交互会话的退出方式。

CPython 从 3.13 起提供新版交互界面。在这个界面中，还可以单独输入：

```text
exit
```

或者：

```text
quit
```

新版交互界面会把它们作为退出操作处理，不要求添加调用括号。经典基本交互界面仍然存在，其他工具提供的交互界面也可能有不同规则。

**裸写 `exit` 能退出，是该交互界面的便利功能，不是“Python 函数调用可以普遍省略括号”的语言规则。**

例如，普通情况下：

- `math.sqrt` 表示取得这个函数。
- `math.sqrt(36)` 才表示调用它，并传入 `36` 进行计算。

也不能把新版交互界面中的裸 `exit` 快捷行为直接套到普通 `.py` 脚本中。这里讨论的 `exit`、`quit` 及其调用形式，是面向交互操作的辅助功能。

成功退出后，提示符会回到 PowerShell 的 `PS ...>`，而不是继续停留在 `>>>`。
