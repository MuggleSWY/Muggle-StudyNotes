# 怎样分析一个实际 AI 需求

## 一、先说清使用者要完成什么事

“想用 AI 查设备手册”只说明了一个大致方向。真正影响设计的是：谁在什么情况下使用它，手头有什么信息，需要拿着结果完成什么事，以及凭什么知道这件事做成了。

例如，可以把目标表述成：“当使用者拿着设备型号和一个问题来查询时，帮助他找到适用于这台设备、能够回应这个问题的手册内容，并能回到原文核对；目前的信息不足以判断时，能看出还缺什么。”这里的“找到”比“系统返回一段文字”多两层要求：内容与问题有关，而且内容适用于正在查询的设备。

目标确定之后，再考虑关键词查询、文字匹配模型或二者结合。它们都是**候选方法**；“是否用了模型”本身不是成功标准。

## 二、把目标落实为输入、输出和条件

| 要分析的项目 | 放到设备手册查询中怎么问 |
| --- | --- |
| 输入 | 使用者提供的是设备型号、故障码、问题描述，还是其中一部分？判断适用性所必需的信息是否齐全？ |
| 可用资料 | 有哪些手册？能否读出所需内容？能否确定手册适用的型号、版本，并定位到原文？ |
| 有效输出 | 找到哪些相关段落？分别来自哪本手册、什么位置，使用者怎样检查它是否适用？ |
| 信息不足时的输出 | 如果几本手册给出的说明不同，而设备版本未知，是需要追问版本，还是可以列出不同条件下的条目？ |
| 能力边界 | 查询手册能够说明“文档在什么条件下怎么写”，仅凭这一结果不能确认现场设备真实发生了什么。 |

必须把“资料可以使用”拆成可核对的条件。**文件能打开，不等于相关文字可以正确读取；文字能读取，不等于这个版本适用于目标设备。** 即使系统准确找到了某段原文，若它只适用于另一型号或版本，也没有完成这次有效查找。

## 三、拆开任务，再安排普通程序、模型和人的职责

一次查找可以拆成几个有不同判断依据的步骤：先弄清目标设备和问题，再选出可能适用的手册，从中找候选段落，最后让使用者核对出处、上下文和适用条件。

例如，设备型号和版本号若已明确录入，且手册有可靠的对应标记，普通程序可以按明确规则筛选。若用户提供的是清楚的故障码或原文术语，关键词查询也可以作为简单的候选方案。筛选和搜索的依据均不充分时，需要补充信息；模型不能补出资料里并不存在的型号或版本关系。

**文字匹配模型**在这里指帮助比较问题与文档片段在文字含义上是否相关的模型。例如，使用者问“开机后屏幕一直黑着”，手册用的表述却是“启动后显示屏无画面”。这里有两个相关任务：[[10-数据模态与任务类型#七、检索、排序与生成：找内容、排顺序、组织内容|检索要找出哪些段落相关，排序要决定先展示哪一段]]。文字匹配模型可以为这两步提供依据。能否在实际手册中找得更好，要通过测试判断。含义相近也不保证型号、版本和说明都正确。

从[[12-算法、模型、服务、产品与系统的区别#八、不能把整套产品的能力全部算到模型身上|整套查询系统的分工]]看，程序还要接收查询、传递设备信息、展示原文位置，并处理查不到的情况。即使模型给出了合适的候选，如果程序传错了设备型号，或界面不显示出处，使用者仍可能拿不到可用结果。

## 四、规定怎样才算成功，并检查失败的影响

可以围绕一次具体查找约定成功标准：结果回应了问题，来源可以核对，适用条件与目标设备相符，使用者能够据此完成查找。若现有资料不足以给出可靠结果，应能说明“没有找到可核对的适用条目”或提示需要补充哪项信息。**暂时没找到，不等于能确认手册里绝对没有；系统返回了内容，也不等于查找成功。**

失败不只有“没有结果”。例如，没找到已有的正确条目会使人重新翻手册；把另一版本的相似说明当成适用条目，则可能让人采用不合适的操作。两者的后果不同，因此不能只数“有多少次给出了结果”。需要检查什么错误、是否需要人工复核，应结合结果会被怎样使用来决定。

## 五、怎样比较关键词查询与文字匹配模型

**先把比较对象和成功标准固定下来。** 给两种方法同一批查询、同一范围和版本的手册、同样的已知设备信息，用同一套标准判断结果。可以同时选取措辞贴近原文的问题、说法不同但意思相近的问题，以及资料不足的问题。评价前应知道怎样根据适用原文判断结果，不能把任一候选方案的输出直接当作正确答案。

| 比较维度 | 实际要看什么 |
| --- | --- |
| 查找质量 | 找到的段落是否回应问题，型号、版本是否适用，能否回到原文核对；对信息不足的问题是否作了恰当处理。 |
| 完成时间 | 从发起查询，到使用者找到并核实适用内容，总共花多久。系统响应时间可以单独记，但不能代替全过程时间。 |
| 失败与返工 | 哪些题查不到、找错版本或返回无关段落？使用者是否需要改写问题、翻看更多段落或重新查找？ |
| 成本 | 在相同使用规模下，各方案需要多少运行或调用成本，以及多少核对、返工时间；有无足够改进来抵偿新增成本。 |

例如，一个方案先返回结果，但把多个版本的相似段落混在一起；使用者仍得逐项排除。另一个方案稍晚返回，却直接给出适用原文。这里需要分开衡量[[13-AI系统的基本生命周期与人员分工#五、验证：效果、速度与完整流程要分别检查|程序的响应时间和使用者完成查找的时间]]。仅凭前者“响应更快”，无法判断使用者是否更早找到适用的段落。应分别记录成功的查找耗时和未成功的查找，避免只统计顺利完成的情况。

## 六、把未验证的假设留下来

“手册覆盖目标设备”“资料标注的版本可靠”“文字匹配能减少措辞不同造成的漏查”“增加模型后能缩短总查找时间”，是四个不同的判断，需要不同证据。前两项先检查资料，后两项用同条件的案例比较。若试验只覆盖一个型号，也应把结论限定在已测范围，不能写成所有型号都适用。

一份有用的需求分析，最后应能说清：**要帮谁完成什么事、凭什么信息完成、各步骤由谁承担、怎样识别成功和失败，以及还需要什么证据来选择方法。** 在证据不足时，保留候选方案和待验证项，比提前给某种方法下结论更准确。
