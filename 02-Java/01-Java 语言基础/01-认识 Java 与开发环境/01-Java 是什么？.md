# 一、 Java 的基本概念

## 1、Java 是什么？

**狭义的 Java 是一门编程语言；广义的 Java 还可以指围绕这门语言建立的平台和生态**。讨论 Java 时，首先需要确定正在讨论哪一层。

从语言本身看，Java 是一门**通用、高级、以类为基础、支持面向对象和并发编辑、采用静态类型与强类型规则的编程语言**。这些描述分别涉及用途、抽象层次、组织程序的方式和类型检查机制，而不是几个可以互相替代的标签。

"编程语言" 不只是一些英文关键字的集合。它既规定语法，即程序可以怎样书写，也规定==语义==，即这些写法代表什么行为。例如，赋值是什么意思、方法调用如何传递数据、发生异常后控制流程怎样变化，都属于语言需要明确的问题。

## 2、Java 语言、Java 平台与 Java 生态

### 2.1、Java 语言：规定程序如何表达

Java 语言关心的是表达程序的规则，例如变量声明、条件判断、循环、方法、类、接口和异常处理。

`if`、 `class` 、 `return` 等是语言中的关键字；它们的含义由语言规则定义。学习 Java 语言，是学习如何准确表达数据、计算、状态和行为，而不仅仅是记住语法模板。

### 2.2、Java 平台：提供程序运行所依赖的共同基础

**平台可以理解为程序开发和运行所以来的一组约定和能力**。Java 平台属于软件平台，不等于 Windows、Linux 等操作系统。

从初步认识的角度，Java 平台的核心可以看作两部分：==Java 虚拟机与标准 API==。虚拟机提供执行程序的基础机制，标准 API 提供应用能够使用的通用能力。这是概念模型，不是在列出某个安装包的全部文件。

**JVM** 的全称是 **Java Virrtual Machine**，即 ==Java 虚拟机-==。

**API** 的全称是 **Application Programming Interface**，即==应用程序编程接口==。这里的 "接口" 是面向程序提供能力的使用约定，不专指 Java 的 `interface` 语法，也不只指前后端之间的 HTTP 接口。

Java 标准类库提供了大量这样的 API 。例如， `String` 表示字符串， `LocalDate` 表示不带时区的日期， `Files` 提供文件操作的能力。它们是平台类库中的类型，不是 Java 关键字。

这带来一个重要区别：

>语言规定 "程序怎样表达"，类库提供 "可以直接使用的能力"，运行时负责 "让程序实际执行"。

三者相互配合。只有语言规则，而没有相应的工具、运行机制和基础库，并不能直接完成一个现实应用。

### 2.3、Java 生态：围绕平台形成的工具、项目与协作关系

Java 生态不是一个可以一次安装完成的单独软件，而是围绕 Java 技术形成的框架、第三方库、开发工具、平台实现、文档和社区等。

例如：Spring Boot 用于简化 Spring 应用的创建、配合和运行；Maven 用于组织项目构建、管理依赖等，它们服务于 Java 开发，但都不是 Java 语法的一部分。

"技术栈" 与 "语言" 也不等价。一个 Java 后端项目使用数据库、消息服务或部署工具，不意味着这些系统都属于 Java 标准平台，更不意味着它们都由 Java 编写。

## 3、三者在实际项目中如何协作

以一个假设的巡检管理程序为例，可以按职责区分：

|         需求          |     所需层次或承担者      |
| :-----------------: | :---------------: |
| 判断巡检任务能否启动、描述任务状态变化 | 使用 Java 语言编写的业务代码 |
|  处理日期、文本和内存中的数据集合   |     Java 标准类库     |
| 组织 Web 应用、减少框架配置工作  | Spring Boot 等生态项目 |
|  管理依赖、组织编译、测试和打包过程  |    Maven 等构建工具    |
|      执行编译后的程序       |    JVM 及配套运行时     |

# 二、Java 出现的背景

## 1、从设备差异出发，而不是只为 Web 后端而生

Java 最初由 Sun Microsystems 开发，于 1995 年公开发布。它并不是一开始就专门为今天 的 Web 后端或微服务设计的语言。

Java 平台早期面对的问题包括：如何为联网的消费电子设备构建软件，如何适应不同的硬件架构，以及如何交付和执行软件组件。后来，Web 的普及使跨设备分发程序的需求更加突出。

## 2、为什么要在应用与具体机器之间增加一层

不同机器可能使用不同的处理器指令集、操作系统接口和文件系统规则。让应用代码直接适应所有差异，会增加开发和维护成本。

Java 的典型思路是：先把源代码转换为一种统一的中间表示，再由适配目标环境的运行时执行它。这样，应用不必为每一种处理器直接编写一套指令。

```
应用程序面对统一的 Java 平台约定
                ↓
不同环境中的运行时实现这些约定
                ↓
具体操作系统与处理器
```

这也是 "Write Once，Run Anywhere" ——"一次编写，到处执行" 的基本出发点。但它表达的是具有前提的可移植能力，而不是 "任何程序复制到任何机器都必然可用"。

# 三、从源代码到程序执行

## 1、先区分源代码、字节码与机器码

| 概念               | 含义               | 典型形式或面向对象                   |
| ---------------- | ---------------- | --------------------------- |
| 源代码，Source Code  | 使用编程语言表达的程序文本    | Java 源文件通常使用 `.Java` 扩展名    |
| 字节码、ByteCode     | 按 JVM 指令集表达的指令序列 | 通常作为 `.class` 内容的一部分保存      |
| 机器码，Machine Code | 面向某种实际处理器指令集的目标  | 例如面向 X86-64 或 AArch64 的本机指令 |

在常规 Java 开发流程中，源代码鲜卑编译为类文件，随后由 Java 运行时执行。字节码不是另一种写法的 Java 源代码，也通常不是目标处理器能够直接执行的本机指令。

`.class` **不只包含字节码**。它还可以包含类的结构、字段与方法信息、常量池以及其他属性。将它口语化地称为 "字节码文件" 没有问题，但不能因此认为其内容只有指令。

"字节码" 中的 "字节" 也不意味着每条指令总共只有一个字节。JVM 指令的操作码占一个字节，某些指令还带有额外操作数。

## 2、编译：把源代码转换为类文件

**编译，Compilation**，是将一种程序表示转换为另一种表示的过程；编译结果不一定是本机机器码。

在典型 Java 流程中， `javac` 是 Java 编译器：读取源代码，进行相应检查，并生成能够提供 JVM 使用的类文件。这里的 "编译" 主要指**从 Java 源代码到 `,class` 的转换。

```
Java 源文件
例如 InspectionTask.java
          │
          │ Java 编译器，例如 javac
          ▼
类文件
例如 InspectionTask.class
```

这是最简单的示意关系，不是 "一份 `.java` 永远只生成一份 `.class` 的规则 "。源文件中包含多个类型或嵌套类等结构时，可以产生多个类文件。

编译器能够发现语法错误和一部分语义错误，例如某个赋值不符合类型规则；但它不能证明程序符合全部业务需求。一个 "完全可以编译" 的程序，仍然可能算错金额、处理错状态或在运行时失败。

## 3、运行：JVM 不只是 "读取文件然后翻译"

从规范角度看，JVM 是一种抽象计算机：有自己的指令集，以及执行这些指令所需的运行规则。通常安装到计算机上的，是这种抽象机器的具体软件实现。

运行一个常规 Java 程序时，需要完成或按需完成若干工作：读取所需类的表示，进行验证辉哥连接，执行必要的初始化，再执行相应代码。相关活动并不都在程序启动时一次性完成。

```
Java 源代码
    │
    │ 编译
    ▼
.class：字节码 + 类的结构信息
    │
    │ 由 Java 运行时加载并执行
    ▼
JVM 实现与配套类库
    │
    │ 在目标环境中执行相应操作
    ▼
操作系统、处理器及其他硬件
```

==JVM 并不要求类文件一定来自 Java 语言==。只要其他语言的实现能够生成符合要求的类文件，也可以利用 JVM 执行相应程序。因此，Java 语言与 JVM 不是一一绑定的关系。

## 4、为什么既会看到 "解释执行"，也会看到 "即时编译"

**解释执行，Interpretation**，可以理解为运行时根据指令含义完成对应操作，而不是预先把全部程序转换为本机代码。

**即时编译，JIT，Just-In-Time Compilation**，指在程序运行过程中，将适合编译的代码转换为本机机器码，再执行这些机器码。

以 HotSpot 这一 JVM 实现的常见运行方式为例，解释器与即时编译器可以协同工作。运行时收集执行信息，并对值得优化的代码进行编译和优化。这里的 "热点" 通常与代码的运行频率等信息有关，不代表每个方法都必然经历完全相同的固定流程。

```
                         ┌─ 解释执行
已加载的程序代码 ──────────┤
                         └─ 运行中进行 JIT 编译 ─→ 执行本机机器码
```

因此， "Java 是编译型语言还是解释型语言" 不能仅凭一个二选一标签回答：
>Java 源代码通常先被编译为字节码；字节码采用什么执行策略，由具体运行时实现决定。HotSpot 的常见配置会结合解释执行与 JIT 编译。

JVM 规范并没有要求所有实现必须采用解释器，也没有强制要求某一种即时编译器。将 HotSpot 的常见行为直接说成所有 JVM 的必然行为，是把实现与规范混为一谈。‘

## 5、这条执行路线的适用边界

"源代码——>字节码——>JVM 执行" 是理解常规 Java SE 程序的重要模型，但不是所有 Java 部署方式的完整描述。

例如，AOT，Ahead-of-Time Compilation，即提前编译，强调在运行之前完成相应编译。GraaIVM Native Image 可以把应用构建成面向特定操作系统和处理器架构的本机可执行文件，并包含所需的运行时支持。它不等于 "把 `.class` 改一个扩展名"，也不应与普通 JVM 部署方式混为一谈。

# 四、Java 的主要特点及其边界

## 1、跨平台：有条件地减少对目标机器的依赖

### 1.1、跨平台能力来自哪里

Java 的可移植性来自多方面配合：统一的语言规则、统一的类文件格式、标准 API，以及各目标环境中实现这些规则的运行时。

同一份符合条件的类文件，可以交给不同环境中的兼容运行时执行；面向 Windows 的运行时安装包本身，并不会因此自动编程 Linux 软件。

```
                    同一份符合兼容条件的类文件
                     /           |           \
                    ↓            ↓            ↓
             Windows 运行时  Linux 运行时  macOS 运行时
                    ↓            ↓            ↓
              各自适配的操作系统与处理器
```

所以，更准确的理解是：通过分别适配各个平台的运行时，减少应用程序需要自行处理的平台差异。

### 1.2、跨平台不等于跨所有版本

类文件有版本信息。较旧的 JVM 不能仅因为 "也是 JVM"，就执行所有较新版本的类文件。

此外，运行程序还需要满足其依赖的 API 和第三方库文件。即使类文件版本能够被识别，运行环境缺少程序所需的类型或方法，也仍然可能失败。

因此，判断能够部署至少要区分：**类文件兼容性、API 可用性、项目依赖，以及目标环境条件**。仅检查 "机器上有没有 Java 是不够的"。

### 1.3、跨平台不等于运行结果完全不受环境影响

文件路径、权限、可用文件、时区和外部服务等，都可能影响应用行为。以文件系统为例，Java 的 `Path` API 本身就明确说明，其实现与文件系统有关。

假设一个程序把输出位置写死为 `D:\reports\result.txt` ，它依赖了 Windows 风格的路径安排。将程序复制到 Linxu，并不会自动创建含义相同的 D 盘。

再如，程序调用了面向特定系统编译的本机库，便额外引入了平台相关条件；这类部署不能只凭类文件具有可移植格式就判断可以迁移。Native Image 生成的本机程序同样面向具体操作系统和架构。

==跨平台是降低迁移成本的能力，不是免除配置、依赖管理和目标环境测试的承诺==。

## 2、静态类型与强类型：相关，但不是同一个概念

### 2.1、静态类型主要回答 "类型何时确定和检查"

在 Java 中，变量和表达式具有编译器可确定的类型，编译器会据此判断许多操作是否合法，例如某种值能够赋给某个变量、某种类型是否具有需要调用的方法。

这有助于在运行前暴露一部分错误，也为代码补全、重构和静态分析提供基础。

需要区分**变量的类型和变量当前保存的值**，一个变量可以保存不同的合法值，但并不因此在运行中随意改变自己的类型。

Java 的 `var` 允许在特定局部变量声明中由编译器推断类型，但推断发生在编译器；它不是把变量变成 "运行时想装什么就装什么" 的动态类型容器。

### 2.2、强类型主要强调 "必须遵守类型规则"
